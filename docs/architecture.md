# Архитектура

## 1. Что за продукт

ORTA — супер-приложение «Всё рядом»: в одном мобильном приложении такси, платежи и
переводы, маркетплейс с доставкой, услуги и кабинет для бизнеса. Проект начинается с
вертикали такси именно потому, что связка «деньги + реальное время» заставляет решать
самые интересные инженерные задачи:

* деньги нельзя терять и нельзя начислять дважды — значит нужна идемпотентность
  и двойная запись, а не «UPDATE balance = balance - 100»;
* платёж, заказ и сток живут в разных сервисах, а операция одна — значит нужна
  сага с компенсациями, а не распределённая транзакция;
* клиент ретраит запросы на плохой сети, а брокер доставляет сообщения повторно —
  значит и HTTP-слой, и консьюмеры обязаны быть идемпотентными;
* в маркетплейсе нельзя продать один товар дважды — значит сток резервируется,
  а не списывается «на глазок».

## 2. Границы сервисов

| Сервис | Отвечает за | Не знает про |
|---|---|---|
| `api-gateway` | токены, роутинг, rate limit, correlation id | бизнес-логику, БД |
| `account-service` | счётá, леджер, holds — **источник истины по деньгам** | заказы, товары |
| `payment-service` | жизненный цикл платежа, сага, рефанды | балансы (спрашивает account-service) |
| `catalog-service` | мерчанты, товары, сток с резервированием | оплату |
| `order-service` | корзина, заказ, оркестрация checkout | балансы и сток (спрашивает владельцев) |
| `driver-service` | профиль водителя, документы со сроком, право выйти на линию | где водитель находится (позиции — эфемерные, ими владеет dispatch) |
| `dispatch-service` | приём геопозиций, индекс Redis GEO, проекция «кто на линии», поиск кандидатов | профиль водителя (имя и телефон приезжают событием), деньги |

План вертикали такси (см. `docs/adr/0009-taxi-vertical.md`): `trip-service` — агрегат
поездки, котировка, чек и сага. Тарифы и surge живут внутри `trip-service`.

Как устроен поток геопозиций (Ф1):

```
driver app ──POST /api/v1/locations──► api-gateway ──► dispatch-service
                                                          │ 1. кто это? userId -> driverId (проекция)
                                                          │ 2. на линии? иначе 409
                                                          │ 3. координаты возможны? иначе 400
                                                          ▼
                                                   Redis GEO + TTL-запись позиции

driver-service ──driver.events (outbox)──► Kafka ──► dispatch-service ──► проекция «кто на линии»
                                                                          (набор duty + профиль)
dispatcher ──GET /api/v1/dispatch/drivers──► карта: проекция + позиции
dispatcher ──GET /api/v1/dispatch/nearest──► GEOSEARCH по радиусу, фильтр «свободен и свеж»
```

Позиции намеренно не идут через Kafka: точка живёт секунды и никогда не переигрывается,
поэтому её место в Redis. Через Kafka идут только факты — регистрация и смена состояния
водителя.

Правило: данные принадлежат ровно одному сервису, остальные обращаются к нему по
API или получают события. Каждый сервис имеет собственную базу — поэтому «сходить
в чужую таблицу» технически невозможно.

## 3. Поток денег (P2P перевод)

```
client ──POST /api/v1/payments/transfers──► api-gateway
                                             │  JWT, rate limit, X-Correlation-Id
                                             ▼
                                        payment-service
   1. проверить, что счёт-источник принадлежит вызывающему  ──► account-service (public API, токен пользователя)
   2. найти счёт получателя по телефону                    ──► account-service /internal/resolve
   3. создать платёж (INITIATED) + событие payment.initiated (outbox)
   4. зарезервировать деньги                               ──► account-service /internal/holds   (PENDING)
   5. превратить резерв в движение                         ──► account-service /internal/holds/{id}/capture (COMPLETED)
   6. событие payment.completed (outbox) ──► Kafka
```

Если шаг 5 падает — платёж помечается `FAILED`, а hold освобождается (компенсация).
Если падает сам сервис между 4 и 5 — запланированная задача находит «зависший»
платёж, спрашивает у account-service состояние hold и детерминированно завершает
или отменяет его. Деньги при этом не «висят»: hold истекает и счёт возвращается
клиенту автоматически.

Ключевое свойство: **каждый шаг записан до следующего удалённого вызова**. Именно
поэтому сага переживает падение процесса — она восстанавливается по состоянию БД,
а не по состоянию в памяти.

## 4. Поток checkout (маркетплейс)

```
cart ──POST /api/v1/orders──► order-service
   1. заказ PENDING_PAYMENT + order.created (outbox)      ← одна транзакция
   2. резерв стока                                         ──► catalog-service /internal/stock/reservations
   3. платёж мерчанту                                      ──► payment-service /api/v1/payments/merchant
        COMPLETED → заказ PAID + commit стока + order.paid
        FAILED    → release стока + заказ CANCELLED + order.cancelled
        таймаут   → заказ остаётся PENDING_PAYMENT
   4. Kafka: payment.completed / payment.failed ──► order-service доразбирает «зависшие» заказы
```

Шаг 4 — не дублирование, а страховка: синхронный вызов мог не дойти до ответа
(таймаут, рестарт пода), и тогда единственным доказательством того, что деньги
списались, остаётся событие. Обработчик идемпотентен: если заказ уже `PAID`, он
ничего не делает.

## 5. Поток расчётов с мерчантом (выплата)

Покупатель заплатил — но продавец ещё не получил. Это два разных факта, и они
разведены во времени:

```
checkout ──► платёж мерчанту ──► деньги на счёте-подвеске платформы
                                          │
   через hold-period (демо 0s, реально T+1)│
                                          ▼
   MerchantSettlementJob: сгруппировать несозревшие продажи по (мерчант, валюта)
        │  одна транзакция: расчёт + строки settlement_payment + пометка продаж
        │  событие settlement.created
        ▼
   есть счёт выплат? ──нет──► остаётся PENDING: долг зафиксирован и виден
        │ да
        ▼
   account-service /internal/credits: дебет счёта-подвески, кредит счёта мерчанта
        │  referenceType=SETTLEMENT, referenceId=<id расчёта>  ← идемпотентность
        ▼
   PAID + settlement.paid   (или FAILED + settlement.failed → повтор в следующем прогоне)
```

Суммы: `net = gross` (мерчанту — стоимость товаров), `commission` (1.5% по умолчанию)
остаётся платформе, `customerPaid = gross + commission`. Все три хранятся, и оба
тождества проверяются CHECK-ограничениями — выручка платформы становится запросом,
а не таблицей в Excel.

`settlement_payment.payment_id` — первичный ключ: одна продажа физически не может
попасть в две выплаты, даже если планировщик запустится дважды.

## 6. Почему именно так (ключевые решения)

### Транзакционный outbox вместо прямой отправки в Kafka

Прямая отправка — это dual write: либо коммит в БД без события (потеряли), либо
событие без коммита (фантом). Outbox делает изменение состояния и событие одной
транзакцией, а relay публикует их позже, at-least-once:

```
❌ tx.commit(payment); kafka.send(event);   // падение между → событие потеряно
❌ kafka.send(event);   tx.commit(payment); // падение между → событие-призрак
✅ tx { payment.save(); outbox.save(event); } → relay → Kafka
```

Relay забирает строки через `SELECT ... FOR UPDATE SKIP LOCKED`, поэтому его можно
масштабировать на несколько реплик, не получая дублей.

### Идемпотентность на двух уровнях

`Idempotency-Key` (Redis `SET NX`) защищает от повторного HTTP-запроса, уникальные
индексы БД (`payment.idempotency_key`, `account_hold.idempotency_key`,
`stock_reservation.order_id`) — от гонки двух реплик. Первое даёт быстрый ответ
клиенту, второе — гарантию. Без второго уровня любая ошибка в коде Redis-слоя
превращается в двойное списание.

### Двойная запись в леджере

Каждое движение денег — две строки (DEBIT и CREDIT) с общим `transaction_id` и
одинаковой положительной суммой. Инвариант проверяется одним запросом:

```sql
SELECT SUM(CASE WHEN direction = 'CREDIT' THEN amount_minor ELSE -amount_minor END)
FROM ledger_entry WHERE transaction_id = :transactionId;   -- всегда 0
```

Счёт-«подвеска» (`type = SYSTEM`) — это внешний мир: деньги, созданные пополнением
или ушедшие мерчанту. Он может уходить в минус (так и должно быть в двойной
записи), клиентские счета — нет, это запрещено CHECK-ограничением.

### Holds вместо «сначала списать, потом разобраться»

Резервирование отделяет «деньги обещаны» от «деньги ушли». Без него у платежа
только два исхода: списать заранее и потом возвращать (плохой UX и лишние
движения) или списать в конце и иногда узнавать, что денег уже нет.

### Резервирование стока вместо декремента

`available = on_hand - reserved`. Покупатель резервирует товар на время оплаты;
оплатил — commit (on_hand и reserved уменьшаются), не оплатил — release
(уменьшается только reserved). Брошенная корзина не «съедает» товар, а
конкурентные покупатели не могут купить последнюю единицу.

## 6. Наблюдаемость и эксплуатация

* **Correlation id** — один на запрос: генерируется в шлюзе, едет в заголовке,
  попадает в MDC логов и в headers каждого Kafka-события. Позволяет собрать всю
  историю операции по одному идентификатору.
* **RFC 7807** — единый формат ошибок с машинным `code`; клиент не разбирает текст.
* **Actuator + Prometheus** — health/readiness/liveness по каждому сервису,
  метрики с тегом приложения.
* **Бизнес-метрики** — технические метрики говорят, что сервис жив; эти говорят,
  что жив продукт. Соглашение об именах: `taxi.<домен>.<факт>`.
  * `taxi.settlement.debt.minor` — сколько платформа должна мерчантам **прямо
    сейчас**. Число, которое только растёт, означает, что выплаты сломаны, и это
    видно до звонка мерчанта.
  * `taxi.settlement.overdue.count` — долг старше суток.
  * `taxi.outbox.pending` — события, записанные, но не доехавшие до Kafka.
    Рост означает, что relay встал, а все потребители молча работают на устаревших
    данных.
  * `taxi.payment.outcome{type,status,currency}` и
    `taxi.payment.failed{reason}` — воронка успешности платежей и **причины**
    отказов: «платежи падают» — это факт, «падают с INSUFFICIENT_FUNDS» — решение.
  * `taxi.reconciliation.findings{kind}` — расхождения данных. Здоровое значение
    строго ноль.
* **Сверка (reconciliation)** — фоновая проверка инвариантов, которые уже держат
  код и БД: расчёт обязан быть подкреплён строками `settlement_payment`, суммы
  расчёта обязаны сходиться, возвраты не могут превышать платёж, завершённый платёж
  обязан знать время завершения. Находки только логируются и попадают в метрику —
  автоматически «чинить» деньги опаснее, чем сообщить о расхождении человеку.
* **DLT** — исчерпавшие ретраи записи уходят в `<topic>.DLT`, их видно и можно
  переиграть; «молчаливая потеря» исключена.
* **Аудит** — `payment_transition` и `order_status_history` хранят не текущее
  состояние, а путь к нему: на вопрос «кто это сделал и когда» отвечает БД.

## 7. Что осталось бы сделать для реального продакшена

Честный список того, что сознательно упрощено в этом проекте. Сделанное вынесено
отдельно, чтобы список не превращался в вечный список долгов.

**Уже закрыто:** расчёты с мерчантами и выплаты (ADR 0007), лимиты и антифрод с
аудитом доступа поддержки, бизнес-метрики и фоновая сверка данных, асимметричные
токены (RS256 + JWKS, `docs/identity.md`).

Осталось:

1. **Service-to-service** — общий секрет `X-Internal-Token` вместо mTLS/mesh.
2. **Разделение платежа между мерчантами** — сейчас один заказ оплачивается одному
   продавцу (ADR 0008: решение, план и цена отсрочки).
3. **Поиск** — Postgres FTS закрывает каталог до сотен тысяч товаров; дальше —
   выделенный поисковый индекс и CDC из каталога.
4. **Схема событий** — JSON с «терпимым к изменениям» чтением; при росте числа
   команд-потребителей нужен schema registry и версионирование контрактов.
5. **Лимиты по умолчанию** — лимит ставится оператором; сидировать потолок
   существующим кошелькам — продуктовое решение, а не техническое.
6. **Мультирегион и БД** — репликация, партиционирование леджера, RPO/RTO,
   регулярная сверка с внешними провайдерами (внутренняя сверка уже есть).
