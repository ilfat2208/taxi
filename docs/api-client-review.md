# Как работают с API три приложения Dihan Market — и что из этого взять ORTA

Разбор по трём живым проектам на диске: клиентское приложение покупателя (`C:\dihanmarket`),
приложение курьера (`C:\Delivery Man App`), приложение магазина (`C:\Vendor app`). Все три —
Flutter, все три работают с одним Laravel-бэкендом `dihanmarket.kz`, рядом с которым стоит
админка (`http://dihanmarket/admin`), которую мы уже смотрели как эталон интерфейса.

Ниже — что именно они делают с API, какие приёмы стоит перенести в ORTA, а какие — наоборот,
не копировать. В конце — что из этого уже сделано в ORTA (эндпоинт `GET /api/v1/config`) и что
осталось.

## 1. Слой работы с сетью у них

Все три приложения используют одинаковый каркас (это одна кодовая база 6amTech, размноженная по
ролям):

```
lib/api/api_client.dart      единый HTTP-клиент
lib/api/api_checker.dart     единая обработка ошибок
lib/api/local_client.dart    офлайн-кэш ответов (Drift/SQLite + SharedPreferences)
lib/util/app_constants.dart  список эндпоинтов и имена заголовков
lib/features/<фича>/domain/services/<x>_service.dart      бизнес-слой
lib/features/<фича>/domain/repositories/<x>_repository.dart  вызовы API
lib/features/<фича>/presentation/controllers/…             состояние (GetX)
```

Объём API: **159 эндпоинтов** у клиента, **165** у магазина, **23** у курьера — все строкой в
одном файле констант, пути вида `/api/v1/...` с префиксом роли (`/customer/...`, `/vendor/...`,
`/delivery-man/...`).

### Что сделано хорошо

1. **Один keep-alive клиент на всё приложение.** `final http.Client _httpClient = http.Client();`
   с комментарием «TCP/TLS-соединение переиспользуется между запросами вместо нового handshake на
   каждый вызов». Таймаут 40 секунд на каждый вызов, отдельно переопределяемый.
2. **Контекст запроса живёт в заголовках, а не в каждом теле.** Центральный `updateHeader()`
   собирает набор: `zoneId` (JSON-массив зон!), `moduleId` (вертикаль), `X-localization` (язык),
   `latitude`/`longitude` (приблизительная геопозиция) и `Authorization` — только если токен есть.
   Один маркетплейс на много городов и вертикалей получает фильтрацию каталога и переводы, не
   меняя ни одного тела запроса.
3. **Серверная конфигурация на старте.** Все три приложения первым делом зовут `GET /api/v1/config`
   и берут оттуда то, что является решением бизнеса, а не экраном: способы оплаты, валюты, модули,
   включённые функции, адрес websocket, ключи и темы, ссылки на «О нас» и условия. Приложение не
   хардкодит список способов оплаты и не ломается, когда платформа меняет правила.
4. **Единая обработка 401.** `ApiChecker.checkApi(response)`: на 401 — очистить пользовательские
   данные, сбросить избранное, уйти на начальный маршрут; на остальных ошибках — показать сообщение
   сервера. Один вызов после каждого запроса, нигде не размазано по экранам.
5. **Сетевой сбой — это значение, а не исключение.** При любом `catch` клиент возвращает
   `Response(statusCode: 1, statusText: 'connection_to_api_server_failed')`. Экраны не падают, а
   показывают понятный текст; отдельный код «1» отличает «нет сети» от «сервер ответил 500».
6. **Тело запроса чистится перед отправкой.** `postData` выбрасывает поля с `null` и пустой строкой:
   форма с незаполненным полем не отправляет `"field": ""` и не получает ошибку валидации на пустом
   месте.
7. **Multipart с двумя ветками (web/native)** — загрузка картинок и документов: на веб-платформе
   файл читается в байты, на устройстве стримится из файла; документы отдельным типом
   `MultipartDocument`.
8. **Офлайн-кэш ответов.** `LocalClient.organize()` (Drift/SQLite + SharedPreferences, TTL 7 дней)
   оборачивает тело в `{ts, body}`, а репозитории принимают `DataSourceEnum {client, local}` — то
   есть выбор «сеть или кэш» сделан явным параметром на каждом вызове, а не спрятан в декораторе.
9. **Push и его отвязка.** FCM-токен уходит на сервер при логине (`fcm_token` в теле) и отдельным
   вызовом `update-fcm-token`; при выходе отправляется **сигнальная строка `'@'`** — устройство
   снимается с учёта. Подписки на топики по зонам и ролям (`subscribeToTopic(zoneTopic)`,
   топики курьера), чтобы рассылка не шла всем.
10. **Real-time настраивается сервером.** В конфиге приходит `websocketStatus`, `websocketUrl`,
    `websocketPort`, `websocketKey` — переключение на сокеты не требует релиза приложения. Пока
    сокетов нет, приложение опрашивает: у магазина диалог нового заказа звонит `Timer.periodic(3 s)`,
    детали заказа обновляются раз в 10 секунд.
11. **Гостевая сессия.** Аноним получает `guest_id`, который отправляется вместе с логином, а после
    входа очищается — корзина и история просмотров не теряются при регистрации. Плюс `POST
    /api/v1/zone/check` — проверка, что адрес вообще обслуживается, **до** оформления заказа.

### Что копировать не надо

| Приём | Почему плохо |
| --- | --- |
| **`{"_method": "put"}` в теле POST** вместо настоящего `PUT`/`PATCH` | Laravel-привычка. Ломает кэширование, инструменты и семантику: у них есть `putData`, но половина вызовов идёт через POST с подменой метода |
| **Токен в query-строке**: `GET /delivery-man/profile?token=…`, `/order?token=…` | Токен попадает в логи прокси, в историю, в Referer. В других вызовах те же данные ходят через `Authorization: Bearer` — то есть это не осознанное решение, а разные руки |
| **Нет refresh-токена** | 401 = полный выход. Для продуктов с оплатой это потеря корзины и адресов на ровном месте |
| **Ошибки как `statusText`** | Тип ошибки теряется: `ErrorResponse` разбирается только для одного шаблона `{errors:[{code,message}]}`, полевые ошибки валидации до формы не доходят |
| **Пагинация ad hoc** | Laravel-конверт `{current_page, data, per_page, total}` читается в каждом контроллере по-своему, общего типа страницы нет |
| **Кэш без инвалидации** | `LocalClient` умеет только «положить» и «достать по ключу», тегов и сброса по событию нет — после изменения заказа кэш живёт до TTL |
| **Загрузка без прогресса** | Файл читается целиком в память, прогресса нет: на мобильном интернете пользователь видит «висит» |

## 2. Как это соотносится с ORTA

Клиенты ORTA устроены иначе и в нескольких местах уже строже:

| Возможность | Dihan (три приложения) | ORTA |
| --- | --- | --- |
| Слои | контроллер → сервис → репозиторий → api client | `feature/*ViewModel` → `data/repo` → `data/remote` (Retrofit) — плюс `core/*` |
| Типы ошибок | `statusText` строкой | RFC 7807 → `ApiError` + `ApiErrorMapper` (и на веб, и на Android) |
| Повтор запроса | нет | `Idempotency-Key` на денежных операциях (веб и Android) + `IdempotencyGuard` на сервере |
| Трассировка | нет | `X-Correlation-Id` от клиента и через шлюз до сервисов |
| Сессия | токен в SharedPreferences | сессия с абсолютным сроком, скидка 15 с до истечения, глобальный 401-обработчик |
| Деньги | числа как есть | минорные единицы и `Money` на всех уровнях |
| Серверная конфигурация | **`GET /api/v1/config`** у всех трёх | **не было** — добавлено этим изменением |
| Push, офлайн-кэш, гость, i18n, real-time-конфиг | есть | нет |

Отсюда список того, что имеет смысл перенести, по убыванию пользы:

1. ~~Серверная конфигурация~~ — **сделано** (см. §3).
2. **Push-уведомления** — регистрация токена устройства, топики по ролям (водитель/курьер/оператор),
   отвязка при выходе. Нужен эндпоинт токена устройства и FCM-проект; в ORTA нет ни того, ни другого.
3. **Гостевая сессия для корзины** — покупка без регистрации с переносом корзины в аккаунт; сейчас
   корзина ORTA требует роли CUSTOMER.
4. **Офлайн-кэш на клиенте** — для витрины и справочников; в ORTA кэша нет вовсе, при отсутствии
   сети экран показывает ошибку.
5. **Конфиг real-time** — когда появится поток позиций водителя; пока ORTA опрашивает, и это
   осознанно (см. `docs/taxi-roadmap.md`).
6. **Проверка зоны до заказа** — для ORTA это проверка, что адрес в городе пилота; сейчас сервис
   просто считает расстояние.

## 3. Что уже сделано в ORTA по итогам разбора

Добавлен публичный `GET /api/v1/config` — тот самый стартовый вызов, который есть у всех трёх
приложений, но которого не было у нас. Он собирается из настоящих данных, а не копирует их:

* `platform` — имя, версия API, валюта, список валют, роли, время жизни токена, режим identity и
  издатель: всё берётся из тех же `SecurityProperties` и `Roles`, которыми шлюз проверяет запросы;
* `verticals` — вертикали (такси, записи, маркет) с базовым путём и **анонимной** точкой входа;
* `tariffs` — прайс-лист из trip-service (`GET /api/v1/trips/tariffs`, читается из
  `taxi.trip.tariffs`, то есть из того же объекта, которым считается цена);
* `paymentMethods` — способы оплаты из payment-service (`GET /api/v1/payments/methods`): баланс
  реализован, карта объявлена планом с причиной, комиссии — из `taxi.payments.*` в базисных пунктах;
* `features` — честные флаги того, чего нет: карты (выводится из ответа payment-service),
  push, websockets, локализация, зоны доставки — с пояснением по каждому;
* `anonymousPaths` — список путей, которые шлюз действительно пускает без токена; он же используется
  в цепочке безопасности (`GatewayPublicPaths`), чтобы клиент не получал вторую, «написанную руками»
  версию правды.

Два решения, которые отличают его от Dihan-версии:

* **Частичный ответ лучше отказа.** Если trip-service молчит, `tariffs` приходит как
  `{"available": false, "reason": "..."}`, а остальные блоки на месте: один медленный сервис не
  оставляет клиента без всей конфигурации.
* **Недоступное объявлено, а не спрятано.** Флаги `features` названы прямо, чтобы клиент нарисовал
  «скоро», а не кнопку в пустоту.

Проверки: `TariffControllerTest` (тарифы совпадают с конфигурацией, изменение конфигурации видно в
ответе), `PaymentControllerMethodsTest` (баланс работает, карта — план с причиной, комиссии из
конфигурации), `PlatformConfigServiceTest` (шесть тестов: платформенные факты, блоки-ответы
сервисов, недоступный сервис стоит одного блока, флаг карт следует за payment-service, кэш,
публикация анонимных путей).

## 4. Что из чужого кода мы сознательно не берём

* Подмена метода `_method: put` — у нас настоящие `PUT`/`POST`, и это часть контракта.
* Токен в query-строке — у нас только `Authorization: Bearer`.
* Строковые ошибки без кодов — у нас RFC 7807 с `code`, `correlationId` и полями валидации.
* Своя пагинация в каждом экране — у нас общий `PageResponse` на сервере и `Page<T>` на клиенте.
* Кэш без инвалидации — если будем делать офлайн, делаем с тегами и сбросом по событиям, иначе
  пользователь читает устаревший заказ и звонит в поддержку.
