# ORTA Taxi: план работ

Документ отвечает на вопрос «что нужно сделать, чтобы первая вертикаль ORTA —
такси — заработала». Он опирается на то, что уже реализовано и проверено, и честно
разделяет: что переиспользуется почти без изменений, что пишется с нуля и в каком
порядке.

Коротко: **денежный контур, идемпотентность, события и безопасность уже есть — их
переиспользуем целиком. Новое — это real-time (геопозиции, офферы, пуши), матчинг,
тарифы и предметная область водителя.**

---

## 1. Почему текущий код — хороший фундамент

| Уже есть | Куда идёт в такси |
| --- | --- |
| Лежджер с двойной записью, holds (reserve/capture/release), suspense-счёт | Преавторизация поездки при назначении водителя, списание по завершении, комиссия платформы, компенсации за отмену |
| `payment-service`: сага, рефанды, сверка (reconciliation), `MerchantSettlement` + `MerchantSettlementJob` | Выплаты водителям: `gross − commission = net` — это ровно та же механика, что расчёт с мерчантом |
| Счёт водителя — обычный счёт в `account-service` | Выплата водителю = уже существующая операция `PAYOUT` со счёта suspense. Новый код леджжера не нужен |
| Transactional outbox + `OutboxRelay` (SKIP LOCKED) + consumer dedup + DLT | Все события поездки получают надёжную доставку «бесплатно» |
| `IdempotencyGuard`, `Idempotency-Key`, дедуп в БД | Принятие оффера, отмена, повтор списания при сетевом сбое |
| RFC 7807 + `correlationId` + `ApiProblem` | Контракт ошибок новых сервисов, разбор инцидентов поддержкой |
| JWT (HS256/RS256 + JWKS), `AuthenticatedUser.canAccess`, `InternalApiTokenFilter` | Роли `DRIVER` и `DISPATCHER` добавляются в `Roles`, ничего больше менять не нужно |
| `CheckoutSagaService` с компенсациями | Образец для `TripSagaService` (отмена на разных стадиях) |
| Пара (merchant/товар/сток) в `catalog-service` | Водитель, авто, документы со сроком действия — та же форма агрегата |
| Лимиты и velocity в `account-service` | Антифрод промокодов и подозрительных списаний |
| Android-клиент (NetworkModule, ApiErrorMapper, Money, IdempotencyKeyHolder, LiveBackendTest) | Каркас для приложений пассажира и водителя |
| Web + Playwright, ops-роль SUPPORT + аудит | Диспетчерская консоль и разбор инцидентов |
| `scripts/e2e-*.ps1` + CI | `scripts/e2e-trip.ps1` и job для новых сервисов |

Оценка: это экономит не «дни», а месяцы — типовые для такси-платформы вещи (деньги,
идемпотентность, события, безопасность) уже сделаны и покрыты тестами.

## 2. Карта понятий: что меняется в домене

| Маркетплейс (сейчас) | Такси (нужно) |
| --- | --- |
| Товар, сток, корзина | Тариф, класс авто, зона (геозона), surge |
| Заказ (`order`) | Поездка (`trip`): pickup → dropoff, расстояние, время |
| Checkout-сага | Сага поездки: заявка → поиск → назначение → подача → поездка → завершение/отмена |
| Мерчант, выплата мерчанту | Водитель, авто, смена, выплата водителю |
| Резерв стока | Резерв (hold) денег пассажира; резерв водителя — «один активный заказ» |
| Срок доставки | ETA: подача, поездка |
| — | Геопозиции в реальном времени, офферы, пуши |

## 3. Целевая архитектура

### Новые сервисы

| Сервис | Ответственность | БД |
| --- | --- | --- |
| `trip-service` | Агрегат поездки, стейт-машина, котировка (пиннинг цены), чек, сага | `taxi_trip`, схема `trip` |
| `dispatch-service` | Поиск кандидатов, офферы с таймаутом, назначение, ETA-ранжирование | `taxi_dispatch`, схема `dispatch` + Redis |
| `location-service` | Приём геопозиций, Redis GEO, треки поездок, геозоны | `taxi_location`, схема `location` + Redis |
| `driver-service` | Водители, авто, документы (со сроком), смены, рейтинги | `taxi_driver`, схема `driver` |
| `pricing-service` | Тарифы, surge-множители, котировки | сначала **внутри** `trip-service` |

> `pricing-service` и `location-service` на старте можно не выделять: тарифы живут в
> `trip-service`, приём позиций — в `dispatch-service`. Выделять, когда появится причина
> (своя нагрузка, свой цикл релиза). Это не «навсегда», а порядок работ.

### Что остаётся как есть

`account-service`, `payment-service`, `api-gateway`, все `platform/*`, `catalog-service` и
`order-service`. Shop-вертикаль **замораживаем** (не удаляем): она уже покрыта тестами,
работает и подтверждает универсальность платформы. Такси становится основной вертикалью.

## 4. Решения, которые нужно принять до кода

| # | Решение | Рекомендация | Почему |
| --- | --- | --- | --- |
| 1 | Гео-стек | **Redis GEO** для горячего поиска + **PostGIS** в существующем Postgres для треков и геозон | Redis уже есть, `GEOSEARCH` решает «кто рядом» за миллисекунды; PostGIS даёт историю поездки для спора и аналитики |
| 2 | Схема матчинга | **Веер на 3 водителей, первый принявший выигрывает** | Последовательные офферы медленнее; гонка решается инвариантом в БД, а не блокировками в приложении |
| 3 | Провайдер маршрутов | OSRM (self-hosted) для dev/тестов и абстракция `RoutingClient`; в прод — Yandex/Google | В тестах не должно быть внешних зависимостей; **лицензия на отображение маршрутов** — отдельное юридическое решение |
| 4 | Real-time | WebSocket-ручка в существующем WebFlux-шлюзе (`/ws/rider`, `/ws/driver`) + Redis Pub/Sub для fan-out | Не плодим сервис; шлюз уже реактивный, JWT-валидация на хендшейке переиспользуется |
| 5 | Push | FCM (+ HMS для Huawei) для офферов | Оффер обязан приходить на заблокированный экран, иначе водители пропускают заказы |
| 6 | Города и тарифы | Один город (Шымкент — пилотный город ORTA), 2 класса (эконом, комфорт) | Мультигород и мультикласс — это данные, а не архитектура; расширяется без переделок |
| 7 | Фискализация | Вне кода, но влияет на модель чека: ОФД/ККМ (например, Webkassa) | Чек в такси в РК обязателен; лучше заложить `receipt` как отдельную сущность сразу |
| 8 | Судьба `catalog`/`order` | Заморозить, не удалять | Регресс не нужен, а вертикаль уже проверена e2e |

## 6. Денежный поток поездки

1. **Котировка.** `POST /api/v1/trips/quote` → тариф + маршрут → цена. Ответ содержит
   `quoteId`, TTL 90 секунд и HMAC-подпись, чтобы клиент не мог подделать сумму.
2. **Заявка.** `POST /api/v1/trips` с `Idempotency-Key` и `quoteId`. Деньги не трогаем.
3. **Назначение.** Водитель принял → `hold` на `quote.total` в `account-service`
   (`reserve`). Не хватило денег → `422 INSUFFICIENT_FUNDS`, поездка не стартует и не
   создаёт долгов. Это ровно та механика, что уже работает в маркетплейсе.
4. **Подача и поездка.** Ожидание сверх бесплатных минут тарифицируется (`waiting_s`).
5. **Завершение.** Пересчёт по факту (расстояние/время) → `capture` холда:
   `RIDE_PAYMENT` (пассажир → suspense), затем начисление водителю и комиссия платформы.
   `driver_net + platform_commission == fare` — инвариант, который проверяется в e2e.
6. **Отмена.** По политике: до подачи — `release` холда; после — `cancellation_fee`
   и компенсация водителю (проводки со suspense).
7. **Выплата водителю.** Settlement-джоба (аналог `MerchantSettlementJob`) суммирует
   заработанное за период и делает `PAYOUT` на счёт водителя — обычный перевод внутри
   леджжера.

Новые значения `LedgerOperation`: `RIDE_PAYMENT`, `RIDE_REFUND`, `CANCELLATION_FEE`,
`DRIVER_ACCRUAL`, `DRIVER_PAYOUT` (последнее, вероятно, уже покрывается `PAYOUT`).

## 7. Реальное время и гео (главный новый риск)

* **Приём позиций.** Водитель шлёт позицию раз в 4 секунды (батчами) по WebSocket или
  `POST /api/v1/locations`. Пишем в Redis GEO с TTL (водитель пропал → автоматически
  выпадает из поиска) и раз в ~15 секунд сэмплируем в Postgres для трека.
  **Сырые GPS-точки через Kafka не гоняем** — это дорого и не нужно.
* **Поиск кандидатов.** `GEOSEARCH FROMLONLAT … BYRADIUS 3 km ASC COUNT 20`, затем
  ранжирование по **ETA**, а не по прямой: у такси «1 км по прямой» и «1 км через реку» —
  разное время.
* **Fan-out событий.** `trip.events` → Kafka → сервис-нотификатор → Redis Pub/Sub →
  WebSocket-нода. Живой трекинг поездки — Pub/Sub, а не Kafka.
* **Пуши.** Оффер дублируется FCM: водитель может быть в фоне, и WebSocket этого не покроет.

### Защита от двойного назначения

Инвариант держим в БД, а не в коде приложения:

```sql
create unique index trip_one_active_per_driver on trip.trip (driver_id)
  where status in ('ASSIGNED','ARRIVED','IN_PROGRESS');
```

Принятие оффера — условный `UPDATE`:

```sql
update trip.trip set driver_id = ?, status = 'ASSIGNED', version = version + 1
 where id = ? and status = 'SEARCHING' and driver_id is null;
```

Ноль обновлённых строк означает «уже назначен» → `409 TRIP_ALREADY_ASSIGNED`. Истечение
офферов разгребает джоба с `FOR UPDATE SKIP LOCKED` — паттерн уже отработан в `OutboxRelay`.

## 8. API и события (эскиз)

```
POST /api/v1/trips/quote                 котировка (тариф, маршрут, цена, quoteId)
POST /api/v1/trips                       заявка (Idempotency-Key, quoteId)
GET  /api/v1/trips/{id}                  статус, водитель, авто, ETA
POST /api/v1/trips/{id}/cancel           отмена с причиной
POST /api/v1/trips/{id}/rate             оценка водителя
GET  /api/v1/trips?status=…              история поездок

POST /api/v1/drivers/offers/{id}/accept  принять оффер (Idempotency-Key)
POST /api/v1/drivers/offers/{id}/decline
POST /api/v1/drivers/status              ONLINE / OFFLINE
POST /api/v1/drivers/trips/{id}/arrived  подал
POST /api/v1/drivers/trips/{id}/start    начал поездку
POST /api/v1/drivers/trips/{id}/finish   завершил
GET  /api/v1/drivers/earnings            заработок и выплаты

POST /api/v1/locations/batch             пакет позиций водителя

GET  /api/v1/dispatch/trips              (DISPATCHER) живые поездки
POST /api/v1/dispatch/trips/{id}/assign  (DISPATCHER) ручное назначение
POST /api/v1/dispatch/trips/{id}/resolve (DISPATCHER) разбор инцидента, возврат денег
```

Топики: `trip.events` (`trip.requested`, `trip.driver.assigned`, `trip.driver.arrived`,
`trip.started`, `trip.completed`, `trip.cancelled`), `driver.events`
(`driver.online`, `driver.offline`), `dispatch.events` (`offer.created`, `offer.expired`).
Существующие `payment.events` и `settlement.events` используются как есть.

## 9. Клиенты

| Клиент | Что делаем |
| --- | --- |
| Пассажир (Android) | В текущем приложении добавляем вертикаль «Такси»: карта, точки А/Б, выбор тарифа, заявка, трекинг, чек, оценка |
| Водитель (Android) | **Новый модуль** `mobile/driver`: переключатель «на линии», foreground-сервис геолокации, оффер со звуком и обратным отсчётом, навигация во внешние карты, заработок и выплаты |
| Диспетчерская (Web) | Раздел в текущем React-приложении: карта онлайн-водителей, живые поездки, ручное назначение, отмена с причиной, возврат денег — всё с записью в аудит (роль `DISPATCHER`/`SUPPORT`) |

Карты в dev-режиме — MapLibre GL + OSM-тайлы (лицензионно чистый вариант); переход на
коммерческий провайдер — отдельное решение (см. §4, п.3).

## 10. Фазы

Оценка — в итерациях (итерация ≈ 1–3 дня работы с агентами и ревью).

### Ф0. Каркас — 2–3 итерации

ADR `docs/adr/0009-taxi-vertical.md`; новые БД, схемы и расширения в
`infra/postgres/init/01-databases.sql` (`taxi_trip`, `taxi_driver`, `taxi_location`,
PostGIS); роли `DRIVER`, `DISPATCHER` в `Roles`; топики в `KafkaTopics`; роуты в
`api-gateway`; скелеты сервисов в реакторе и `docker-compose`.

**DoD:** `mvnw clean install` зелёный, все контейнеры healthy, `smoke-test.ps1` по-прежнему
проходит, в CI добавлен job новых сервисов.

### Ф1. Водители и живая карта — 3–5 итераций

`driver-service`: регистрация, авто, документы со сроком действия, статус «на линии».
Приём геопозиций, Redis GEO. Экран диспетчера с живой картой.

**DoD:** водитель появляется на карте диспетчера менее чем за секунду после включения
«на линии»; `scripts/e2e-driver-online.ps1`; водитель с истёкшим документом не выходит
на линию.

> Фаза намеренно идёт раньше денег: real-time — самый большой новый риск, и его нужно
> пощупать до того, как на него обопрётся биллинг.

### Ф2. Поездка и деньги — 5–8 итераций

`trip-service`: агрегат, стейт-машина, история переходов, котировка с TTL и подписью,
`hold` при назначении, пересчёт и `capture` при завершении, чек, выплата водителю через
settlement-механику. Ручное назначение диспетчером.

**DoD:** `scripts/e2e-trip.ps1` проводит поездку целиком и проверяет инварианты:
баланс = Σ проводок счёта, каждая транзакция сбалансирована, `authorized == captured`,
`driver_net + commission == fare`, `trip_event` без пропусков статусов.

### Ф3. Автоматический матчинг — 5–8 итераций

`dispatch-service`: поиск кандидатов, веер офферов с таймаутом, расширение радиуса
1→3→5 км, ранжирование по ETA, `NO_DRIVERS_FOUND`, защита от двойного назначения,
WebSocket и пуши.

**DoD:** тест гонки — 10 параллельных принятий дают ровно одно назначение; метрика
времени до первого оффера; `scripts/e2e-dispatch.ps1`; потеря оффера из-за истёкшего
таймаута корректно возвращает поездку в поиск.

### Ф4. Клиенты — 5–8 итераций

Вертикаль «Такси» в приложении пассажира; приложение водителя с foreground-геолокацией;
пуши; живой прогон на двух эмуляторах.

**DoD:** заявка с эмулятора пассажира → оффер у водителя → принятие → подача → поездка →
завершение → чек у пассажира и заработок у водителя. Плюс live-тест по образцу
`LiveBackendTest` для обеих сторон.

### Ф5. Правила и эксплуатация — 4–6 итераций

Политики отмен и штрафов, промокоды, surge по ячейкам, рейтинги, диспетчерские ручки
(переназначить, отменить, вернуть деньги), аудит действий, разбор DLT, дашборды.

### Ф6. Нагрузка и прод — 4–6 итераций

k6: 5000 водителей × позиция раз в 4 секунды; проверка ретеншена и стоимости хранения
треков; секреты, бэкапы и восстановление, Helm/k8s, алерты.

**Итого MVP (Ф0–Ф4) — около 20–30 итераций**; эксплуатационно пригодная версия — 30–45.

## 11. Тесты, метрики, SLO

Тесты по образцу уже существующих:

* **стейт-машина** поездки — как `PaymentStateMachineTest` (запрет переходов назад);
* **точность денег** — property-тесты на целочисленную арифметику тарифа, как `MoneyTest`;
* **гонка назначения** — параллельные `accept` дают одно назначение (аналог
  `IdempotencyKeyHolderTest > concurrent callers observe exactly one key`, но на уровне БД);
* **сага** — падение на каждом шаге и корректная компенсация, как в `CheckoutSagaIT`;
* **live-тесты клиентов** — как `LiveBackendTest`, против живого шлюза;
* **e2e-скрипты** — `e2e-trip.ps1`, `e2e-dispatch.ps1`, `e2e-driver-online.ps1`.

Метрики в принятом стиле `taxi.<domain>.<fact>`: `taxi.trip.requested`, `taxi.trip.matched`
(с таймером до первого оффера), `taxi.trip.completed`, `taxi.trip.cancelled{by}`,
`taxi.dispatch.offers{result}`, `taxi.driver.online`, `taxi.location.ingest`,
`taxi.driver.settlement.paid`.

Целевые показатели: p95 времени до первого оффера < 2 с (город с 50+ онлайн-водителями),
доля назначений без расширения радиуса > 85 %, потерянных позиций < 1 %, нарушений
денежных инвариантов — 0.

## 12. Риски

| Риск | Мера |
| --- | --- |
| Real-time путь (WS + приём геопозиций + пуши) — самый большой новый риск | Вынести в Ф1, до денег; нагрузочный тест до продакшена |
| Двойное назначение водителя | Уникальный индекс в БД + условный `UPDATE`, тест гонки |
| GPS-спуфинг и фейковые поездки | `is_mock_location`, проверка «телепорта» по скорости, отсутствие движения при `IN_PROGRESS`, аномальный ETA |
| Подделка цены клиентом | Подписанная котировка с TTL, цена пересчитывается на сервере |
| Карты и маршруты: лицензия на отображение | Решение до продакшена; в dev — OSM/OSRM |
| Расхождение «котировка ≠ факт» | Допуск зафиксирован, спор решается поддержкой через аудит и трек |
| Регулирование в РК: лицензии, медосмотр, техосмотр, фискальные чеки | Заложить `driver.document` со сроком и `trip_receipt` сразу, интеграция с ОФД — отдельная задача |
| Персональные данные: треки — это ПДн | Срок хранения, доступ по ролям, аудит чтения через существующий support audit |
| Хранение треков дорого | Сэмплирование, агрегация через 90 дней, партиционирование по месяцам |

---

## 13. Чего не делать

* Не выделять `pricing-service` и `location-service` в отдельные сервисы до появления
  реальной причины (нагрузка, свой релизный цикл).
* Не гонять сырые GPS-точки через Kafka.
* Не считать деньги во `double` и не хранить множители как `float`.
* Не писать свою карту, роутинг и геокодер.
* Не строить ML-матчинг до накопления данных — сначала детерминированные правила
  (ETA + честность распределения).
* Не хранить треки поездок вечно.
* Не трогать работающий леджжер ради «универсализации» — расширять значениями операций
  и типами ссылок.
