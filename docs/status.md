# ORTA: промежуточные итоги

Срез состояния проекта на 3 октября 2026 года. Документ отвечает на три вопроса: что уже
работает, чем это проверено и что осталось. Новому человеку в команде его стоит прочитать
после README — здесь собраны числа и границы, а не реклама.

## 1. Что это за продукт

ORTA — супер-приложение: платформа (счета, леджер, платежи, каталог, заказы, идентичность) и
подключённые к ней вертикали. Сейчас реализованы две: **такси** (заявка → подача → поездка →
чек) и **QTime** (запись на услуги: компания → мастер → окно → запись). Маркетплейс из
платформенной части работает как витрина с корзиной и оплатой.

Клиенты: **веб** (React/TS, клиентское приложение + админ-панель + демо-режим) и **Android**
(Kotlin/Compose, платёжный клиент с живыми тестами).

## 4. Unit-тесты бэкенда

Полный прогон реактора 3 октября 2026: **911 тестов, 0 падений, 0 пропущенных** в 112 классах,
`BUILD SUCCESS` за 1 минуту 30 секунд (14 модулей, `./mvnw -B -ntp verify`).

Число проверено двумя способами: по итоговым строкам самого прогона (14 модульных сводок) и по
свежезаписанным отчётам surefire — оба дают 911.

Что покрыто тестами по-настоящему, а не формально:

* **деньги** — целочисленная арифметика в минорных единицах, комиссии, разбор чека поездки,
  инвариант «сумма компонентов равна итогу»;
* **стейт-машины** — платежа, поездки, записи: запрет перехода назад и переход из терминального
  состояния;
* **идемпотентность** — повтор запроса с тем же ключом не двигает деньги второй раз (и на сервере,
  и в живом сценарии, и в Android-тесте);
* **лимиты и антифрод** — отказ приходит **до** резервирования денег;
* **сага заказа** — падение на каждом шаге и компенсация;
* **сверка** — фоновая проверка инвариантов леджера и расчётов находит расхождения (находки только
  логируются и уходят в метрику, ничего не «чинится» молча);
* **границы доступа** — кто видит чужой платёж, кто может вернуть деньги, кто меняет лимиты.

## 5. Что не сделано (честно)

1. **Учебный провайдер идентичности**: `POST /api/v1/auth/token` принимает любой телефон с кодом
   `0000` и выдаёт любую роль, включая ADMIN. Для демо-стенда это удобно, для публичного доступа —
   дыра. Нужен настоящий OIDC (`JWT_MODE=JWKS`) или закрытый на входе `/api/v1/auth/**`.
2. **Автоматический матчинг поездок (Ф3)** — не начат: заявку принимает диспетчер вручную или
   ближайший водитель по радиусу.
3. **Push-уведомления** — нет ни эндпоинта токена устройства, ни FCM: о новом заказе узнают из
   открытого экрана.
4. **Real-time** — опрос вместо сокетов (осознанно для текущего объёма), конфигурация сокетов
   сервером не публикуется.
5. **Офлайн-кэш и гостевая корзина** в клиентах — нет; корзина требует роли CUSTOMER.
6. **Зоны, тарифы по городам, наценки (surge)** — город один, тарифы в конфигурации, `surgeBp`
   всегда 0.
7. **Мониторинга и алертов нет**: метрики отдаются (`/actuator/prometheus`), но Prometheus-сервера
   и Grafana в проекте нет; истории метрик тоже нет — только кумулятивные счётчики.
8. **Аудит действий оператора** — есть аудит чтения (support_audit_record), но не журнал «кто что
   изменил».
9. **Прод-стенд не поднят**: контур готов и проверен по частям, но на сервере не запускался —
   нет домена, TLS, systemd и расписания бэкапов.
10. **Мобильное приложение — только Android**, и только платёжная часть: вертикали такси и QTime
    в нём не реализованы.

## 6. Известные ограничения и «мины»

* **`driver-service` не берёт `Clock`**: сервис вызывает `Instant.now()` сам, поэтому фикстуры
  тестов с абсолютными сроками истекают по календарю. Один такой тест уже падал 3 октября 2026 —
  починен, фикстуры считаются от текущих часов. Правильное решение — внедрять `Clock`, это
  записано в задачи.
* **Расчёт по 480 и 50000**: у каталога рейтинг мерчанта в диапазоне 0…500, у QTime и водителей —
  0…50000. Расхождение шкал в сервисах, в клиенте для каждой есть свой форматтер; лучше свести
  их в сервисах.
* **Статусные рейлы в админке** стоят по одному запросу `size=1` на статус (поездки 9, записи 6,
  заказы 6) — цена честных серверных чисел, кэш 60 секунд.
* **Девять сборок Maven параллельно укладывают сервер** на 4–8 ГБ памяти: в прод-контуре
  параллелизм ограничен, первый деплой — 10–25 минут.
* **Тесты под нагрузкой флакуют**: при одновременном прогоне 38 файлов веба изредка падают
  отдельные сценарии Playwright/React (`TaxiPage`, `TripPage`); в изоляции они зелёные. Лечится
  уменьшением параллелизма в CI, это записано.
* **Порт 5432 на этой машине занят не нашим Postgres**: системный PostgreSQL держит IPv4-адрес,
  а контейнер `taxi-postgres` доступен через IPv6 (Docker Desktop отдаёт его как `[::1]:5432`).
  `scripts/it-local.ps1` ищет рабочий адрес сам, но если задать `-DatabaseHost localhost` вручную,
  тесты уйдут в чужой сервер и упадут пятью ошибками «роль „taxi“ не существует». Теперь скрипт
  проверяет и заданный вручную адрес и падает с понятным объяснением; для запуска без параметров
  он подбирает `[::1]` автоматически.
* **`web-builder` в прод-контуре ставит зависимости при каждой сборке SPA** (pnpm-store не смонтирован):
  на сервере это лишние минуты. Решение — том с кэшем pnpm, записано в задачи.

## 7. Что дальше, по приоритету

1. **Сервер**: довести выкладку до рабочего состояния (домен, TLS, systemd, бэкапы по расписанию) —
   файлы готовы, нужны доступы. Перед публичным доступом закрыть провайдер идентичности (§5.1).
2. **Команда**: репозиторий в Bitbucket, роли и правила PR, Pipelines — см.
   [`collaboration.md`](collaboration.md) и [`../bitbucket-pipelines.yml`](../bitbucket-pipelines.yml).
3. **Push-уведомления** — без них водитель и оператор видят заказ только на открытом экране.
4. **Мониторинг** — Prometheus + Grafana (или хотя бы алерты на health и на рост 5xx из «Пульта»).
5. **Ф3: матчинг** — офферы ближайшим водителям с таймаутом и повтором.
6. **Гостевая корзина и офлайн-кэш** — по разбору чужих приложений
   ([`api-client-review.md`](api-client-review.md)).

## 8. Как запустить и проверить локально

```powershell
# инфраструктура и сервисы
docker compose --profile app up -d --build

# веб: клиент, админка, демо-режим
cd web; pnpm install; pnpm dev        # http://localhost:5173
#   /            клиентское приложение
#   /admin       админ-панель (роль ADMIN или SUPPORT на экране входа, код 0000)
#   /demo        демо-режим: 162 экрана, 8 ролей

# проверки
cd web; pnpm test; pnpm e2e; node e2e/check-admin.mjs; node e2e/check-demo.mjs
.\scripts\e2e-trip.ps1; .\scripts\e2e-qtime.ps1; .\scripts\it-local.ps1
cd mobile\android; .\gradlew.bat testDebugUnitTest
```
