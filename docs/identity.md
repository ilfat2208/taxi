# Идентичность: от общего секрета к RS256 + JWKS

Документ описывает переход с симметричного HS256 (общий секрет во всех сервисах) на
асимметричный RS256 с публикацией публичных ключей через JWKS. Это закрывает пункт 1
списка «что осталось для реального продакшена» в `docs/architecture.md`.

---

## 1. Зачем

Сейчас шлюз подписывает токены общим секретом, и **тот же секрет лежит в каждом сервисе**:
без него сервис не может проверить подпись. Значит любой скомпрометированный сервис
(например, catalog-service) может сам выпустить себе токен с ролью `ADMIN` — для этого
достаточно прочитать переменную окружения. Проверка токена в этом режиме неотделима от
права его выпускать.

В асимметричной схеме:

* приватный ключ есть **только у издателя** (шлюз или внешний OIDC-провайдер);
* сервисы скачивают публичный набор ключей (`/.well-known/jwks.json`) и проверяют подпись
  локально — без обращения к провайдеру на каждый запрос;
* сервис физически не может выпустить токен: у него нет ключа, которым можно подписать.

Бизнес-код при этом не меняется вообще: `AuthenticatedUser`, роли, `@PreAuthorize`,
401/403 в формате RFC 7807 — те же.

---

## 2. Два режима

Режим задаётся свойством `taxi.security.mode`:

| Значение | Подпись | Проверка | Что лежит в сервисе |
|---|---|---|---|
| `HMAC` (по умолчанию) | HS256, общий секрет | HS256, тот же секрет | секрет (**может выпускать токены**) |
| `JWKS` | RS256, приватный ключ издателя | RS256, публичный набор ключей | только публичные ключи |

Полный набор свойств (`taxi.security.*`):

| Свойство | По умолчанию | Назначение |
|---|---|---|
| `mode` | `HMAC` | выбор режима проверки |
| `jwt-secret` | локальный дев-секрет | HS256-секрет, ≥ 32 байт; **нужен только в HMAC** |
| `jwk-set-uri` | — | URL набора публичных ключей; **обязателен в JWKS** |
| `issuer` | `https://identity.taxi.local` | значение `iss` по умолчанию |
| `issuer-uri` | — | ожидаемый `iss`; если задан — перекрывает `issuer` |
| `jwks-cache-ttl` | `5m` | сколько кэшируется скачанный набор ключей |
| `signing-key` | — | **только для издателя** (шлюз): приватный ключ в PEM (PKCS#8) или JWK JSON |
| `jwt-ttl`, `roles-claim`, `cors-allowed-origins`, `public-paths` | как раньше | без изменений |

Обратная совместимость: сервис, у которого задан только `jwt-secret`, работает ровно так,
как работал. `mode` по умолчанию `HMAC`, поэтому ни один существующий конфиг не меняет
поведения — и все прежние тесты остаются зелёными без правок.

## 3. Как переключить

### 3.1 Шлюз (он же издатель в этом демо)

```yaml
taxi:
  security:
    mode: JWKS
    issuer-uri: https://identity.taxi.local
    jwk-set-uri: http://127.0.0.1:8080/.well-known/jwks.json   # свой же эндпоинт
    signing-key: ${JWT_SIGNING_KEY:}                          # PEM или JWK; пусто = ключ на процесс
    jwks-cache-ttl: 5m
```

Через переменные окружения:

```powershell
$env:JWT_MODE = "JWKS"
$env:JWK_SET_URI = "http://api-gateway:8080/.well-known/jwks.json"
$env:JWT_SIGNING_KEY = Get-Content .\keys\gateway-key.pem -Raw   # PKCS#8 PEM
```

В режиме `JWKS` шлюз подписывает токены приватным ключом (RS256), кладёт `kid` в заголовок
JOSE и публикует публичную половину на `GET /.well-known/jwks.json`.

### 3.2 Доменные сервисы

В `services/*/src/main/resources/application.yml` нужные ключи уже есть — достаточно
задать переменные окружения, `jwt-secret` при этом можно **удалить**:

```yaml
taxi:
  security:
    mode: ${JWT_MODE:HMAC}                 # JWT_MODE=JWKS
    jwt-secret: ${JWT_SECRET:...}          # в JWKS не нужен и не читается
    jwk-set-uri: ${JWK_SET_URI:}           # JWK_SET_URI=http://api-gateway:8080/.well-known/jwks.json
    jwks-cache-ttl: ${JWKS_CACHE_TTL:5m}
    issuer: ${JWT_ISSUER:https://identity.taxi.local}
    issuer-uri: ${JWT_ISSUER_URI:}
```

```powershell
$env:JWT_MODE = "JWKS"
$env:JWK_SET_URI = "http://api-gateway:8080/.well-known/jwks.json"
Remove-Item Env:JWT_SECRET        # сервису он больше не нужен
```

### 3.3 Порядок миграции

1. Сначала шлюз: `JWT_MODE=JWKS` + `JWT_SIGNING_KEY`. Старые HS256-токены после этого
   перестают приниматься — клиенты логинятся заново (`POST /api/v1/auth/token`).
2. Затем сервисы по одному: `JWT_MODE=JWKS` + `JWK_SET_URI`. Сервис в JWKS-режиме
   принимает только RS256-токены, поэтому переключать его раньше шлюза нельзя.
3. После переключения всех — убрать `JWT_SECRET` из окружения и из `docker-compose.yml`
   (сейчас он там проброшен во все сервисы; в JWKS-режиме это лишний материал для подписи).

Проверка на старте fail-fast: в HMAC требуется секрет ≥ 32 байт, в JWKS — непустой
`jwk-set-uri`. Сервис в JWKS-режиме **не** падает из-за отсутствующего `jwt-secret` — это и
есть смысл режима; если бы он требовался, сервису пришлось бы держать ключ подписи.

## 4. Ключ подписи

* `taxi.security.signing-key` — приватный ключ в формате **PKCS#8 PEM**
  (`-----BEGIN PRIVATE KEY-----`) или **JWK JSON** (документ с `kty=RSA` и приватными
  параметрами, обычно с готовым `kid`).

  PKCS#1 (`BEGIN RSA PRIVATE KEY`) не поддерживается сознательно: разбор ASN.1 руками в
  провайдере идентичности — худшее место для самодельного кода. Конвертация один раз:
  `openssl pkcs8 -topk8 -nocrypt -in key.pem -out key-pkcs8.pem`. Сервис об этом прямо
  и скажет в сообщении об ошибке.

* Если `kid` в ключе нет, он выводится как **RFC 7638 thumbprint** — хэш от самих
  параметров ключа. Свойство полезное: `kid` стабилен между рестартами, меняется ровно
  тогда, когда меняется ключ, и в заголовке токена всегда оказывается ровно то значение,
  которое опубликовано в JWKS.

* Если `signing-key` не задан, шлюз **генерирует ключ в памяти процесса** (2048 бит) и
  громко пишет об этом WARN. Последствия, о которых нужно помнить в локальной разработке:
  рестарт шлюза делает ранее выданные токены невалидными (в JWKS больше нет ключа, которым
  они подписаны), а два экземпляра шлюза публикуют разные наборы ключей. Для чего-либо
  кроме локального запуска ключ задаётся конфигурацией.

## 5. Ротация ключей

Ротация — это операция издателя, сервисам перезапуск не нужен:

1. Сгенерировать новую пару, присвоить новый `kid` (например `gateway-key-2`).
2. **Опубликовать новый публичный ключ рядом со старым** — в JWKS-документе на время
   ротации два ключа.
3. Начать подписывать новым ключом (в заголовке токена появляется новый `kid`).
4. Держать старый ключ в наборе, пока не истекут все токены, подписанные им
   (`jwt-ttl`, по умолчанию 1 час), и только потом убрать.

Почему это работает без рестартов — правила кэша набора ключей (`JwtSupport.jwksDecoder`):

* набор скачивается один раз и переиспользуется `jwks-cache-ttl` (по умолчанию 5 минут);
  скачивание на каждый запрос поставило бы провайдера идентичности на горячий путь всех
  вызовов и сделало бы его единой точкой отказа платформы;
* обновление происходит, когда кэш пуст, когда истёк TTL (за 30 секунд до истечения
  начинается refresh-ahead) **и когда приходит токен с `kid`, которого в кэше нет** —
  тогда набор перечитывается немедленно, один раз;
* если `kid` в наборе есть, но не подошёл (другой алгоритм, другое назначение ключа),
  это отказ **без** сетевого обращения: иначе любой мусорный токен бил бы по JWKS-эндпоинту;
* одновременные обновления сериализуются, поэтому всплеск запросов после ротации стоит
  одного скачивания, а не одного на запрос;
* если после обновления `kid` всё ещё неизвестен, токен **отклоняется**, а не принимается
  «пока что».

Обратная сторона правила: клиент, который может послать токены со случайными `kid`,
заставит сервис перечитывать JWKS на каждый такой запрос. Поэтому JWKS-эндпоинт обязан
отдаваться с HTTP-кэшированием (шлюз отдаёт `Cache-Control: max-age=<jwks-cache-ttl>`) и
должен быть дешёвым. Это осознанный компромисс nimbus `RemoteJWKSet`, а не недосмотр:
альтернатива — не принимать новые ключи до истечения TTL, то есть ротация с простоем.

## 6. Что защищено тестами

`platform/common-security-core` — `JwtSupportJwksTest`:

* токен, подписанный ключом издателя, проверяется по JWKS-документу того же ключа;
* `kid` в заголовке совпадает с опубликованным ключом;
* токен, подписанный **другим** RSA-ключом, отклоняется; отдельно — попытка использовать
  опубликованный `kid` с чужим ключом (kid — подсказка, а не доказательство);
* неизвестный `kid` отклоняется (после принудительного перечитывания набора);
* `alg=none` отклоняется;
* классическая путаница алгоритмов: HS256-токен, подписанный **публичным** ключом, отклоняется;
* HS256-токен, подписанный общим секретом, тоже отклоняется;
* набор ключей скачивается один раз на множество запросов (кэш работает);
* ротация: новый ключ подхватывается без рестарта ровно за одно дополнительное скачивание,
  старые токены продолжают работать, пока старый ключ опубликован;
* токен другого издателя отклоняется, даже если подпись верна;
* пустой `jwk-set-uri` в JWKS-режиме падает с внятной ошибкой.

`platform/common-security` — `JwksModeSecurityAutoConfigurationTest`: контекст поднимается
**без `jwt-secret`**, RS256-токен проходит, роли через `@PreAuthorize` работают, анонимный
запрос получает 401 в problem+json, чужие ключи / HS256 / `alg=none` / неизвестный `kid`
получают 401.

`services/api-gateway` — `JwksEndpointTest`, `GatewayJwksModeSecurityTest`,
`RsaSigningKeyProviderTest`: эндпоинт JWKS доступен без токена и отдаёт валидный набор
публичных ключей (приватных параметров в ответе нет), `kid` токена совпадает с
опубликованным, шлюз проверяет собственный RS256-токен по реальному JWKS-URL и работает
без секрета, HS256/`alg=none`/чужой ключ отклоняются, HMAC-режим продолжает работать,
PEM/JWK-ключ из конфигурации читается и подписывает проверяемые токены.

## 7. Чего здесь нет

* **Отзыва токенов.** Токен живёт до `exp`; отзыв — это отдельный механизм (короткий TTL +
  refresh, denylist, introspection). Не входит в задачу.
* **Discovery-эндпоинта** (`/.well-known/openid-configuration`) и полноценного OIDC:
  внешний провайдер можно подключить уже сейчас (указать его `jwk-set-uri` и `issuer-uri`),
  но логин останется на `POST /api/v1/auth/token`, пока он не будет заменён.
* **Ротации без ручных шагов.** Ключи публикуются и читаются, но смена ключа — операция
  дежурного: автоматического rollover по расписанию нет.
* **Приватного ключа в secret-хранилище.** `signing-key` приходит из конфигурации или
  переменной окружения; интеграции с Vault/KMS нет.
* **mTLS и service-to-service.** Внутренние вызовы по-прежнему защищены общим
  `X-Internal-Token` (пункт 2 списка в `docs/architecture.md`).
* **Проброса режима в `docker-compose.yml`.** Файл вне рамок этой задачи; при миграции
  контейнеров нужно добавить `JWT_MODE`, `JWK_SET_URI` и (для шлюза) `JWT_SIGNING_KEY`.
