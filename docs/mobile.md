# Мобильный клиент: нативный Android (Kotlin + Jetpack Compose)

`mobile/android` — нативное приложение к тому же шлюзу (`:8080`), что используют web-клиент
и скрипты. Это не мок и не отдельный бэкенд: приложение ходит в те же API с теми же
контрактами — RFC 7807, обязательный `Idempotency-Key`, роли из JWT, ULID-идентификаторы,
деньги в минорных единицах.

Смысл модуля — доказать, что платформенные контракты годятся не только для браузера:
клиент на Kotlin читает те же DTO и так же обрабатывает ошибки, не имея никаких
привилегий перед web-клиентом.

---

## 1. Стек и структура

| Слой | Что используется |
| --- | --- |
| UI | Jetpack Compose, Material 3, Navigation Compose |
| Состояние | MVVM: `ViewModel` + `StateFlow`, без событий-однодневок |
| Сеть | Retrofit + OkHttp + `kotlinx.serialization` |
| Сессия | DataStore Preferences (токен + профиль), очищается по 401 |
| Сборка | Gradle Kotlin DSL, версии в `gradle/libs.versions.toml` |

```
mobile/android/app/src/main/java/kz/taxi/mobile/
  ApiConfig.kt              адрес бэкенда (см. §4) и демо-константы
  core/
    money/Money.kt          форматирование и разбор сумм в минорных единицах (ru-KZ)
    util/PhoneNumbers.kt    нормализация и валидация телефонов
    error/ApiError*.kt      разбор RFC 7807 в человеческий текст на русском
    idempotency/            ключ идемпотентности на одну операцию
    net/                    OkHttp-интерсепторы: Authorization, correlation id, problem-log
    session/                DataStore-хранилище сессии, SessionManager
  data/
    dto/                    контракты API (совпадают с backend-DTO)
    remote/                 Retrofit-интерфейсы по сервисам
    repo/                   репозитории: сеть + маппинг ошибок
  feature/                  login, accounts, transfer, payments, catalog, cart, checkout, orders
  nav/AppNav.kt             граф навигации; стартовый экран выбирается по наличию сессии
```

## 2. Сборка

```powershell
cd mobile\android
.\gradlew.bat assembleDebug      # app\build\outputs\apk\debug\app-debug.apk (~10 МБ)
.\gradlew.bat testDebugUnitTest  # JVM-тесты, бэкенд не нужен
```

Нужен JDK 17 и Android SDK (`ANDROID_HOME`). `minSdk 26`, `targetSdk 34`.
Debug-сборка ставится как `kz.taxi.mobile.debug`, поэтому рядом с release-версией.

## 3. Запуск на эмуляторе

```powershell
$sdk = $env:ANDROID_HOME
& "$sdk\cmdline-tools\latest\bin\avdmanager.bat" create avd -n taxi `
    -k "system-images;android-34;google_apis;x86_64" -d pixel_6
Start-Process "$sdk\emulator\emulator.exe" -ArgumentList '-avd','taxi'
& "$sdk\platform-tools\adb.exe" install -r app\build\outputs\apk\debug\app-debug.apk
& "$sdk\platform-tools\adb.exe" shell am start -n kz.taxi.mobile.debug/kz.taxi.mobile.MainActivity
```

Бэкенд к этому моменту должен быть поднят (`docker compose --profile app up -d`).

## 4. Какой адрес у бэкенда

| Где запущено приложение | Адрес | Как получается |
| --- | --- | --- |
| Эмулятор Android | `http://10.0.2.2:8080` | значение по умолчанию: `10.0.2.2` — это loopback машины-разработчика изнутри эмулятора |
| Физическое устройство по USB | `http://localhost:8080` | `adb reverse tcp:8080 tcp:8080`, клиент умеет `ApiConfig.HOST_LOOPBACK_BASE_URL` |
| Устройство в сети | `http://<IP машины>:8080` | `-Ptaxi.api.baseUrl=http://192.168.x.x:8080` (и хост нужно добавить в `network_security_config.xml`) |
| JVM-тест на хосте | `http://localhost:8080` | тест сам выставляет `-Dtaxi.api.baseUrl` |

Адрес живёт в одном месте (`core/ApiConfig.kt`) и подставляется в `BuildConfig` при сборке:

```powershell
.\gradlew.bat assembleDebug -Ptaxi.api.baseUrl=http://192.168.1.10:8080
```

## 5. Вход в демо-режиме

Dev-провайдер идентичности принимает любой `+7XXXXXXXXXX` с кодом `0000`. Форма входа уже
заполнена демо-номером `+77001234567` и кодом, так что для входа достаточно одного нажатия.
Переключатель «оператор» добавляет в токен роль `ADMIN`, без которой недоступны
демо-пополнение и часть операторских ручек.

## 6. Экраны

| Экран | Что показывает |
| --- | --- |
| Вход | телефон + код, ошибки контракта (401 `UNAUTHORIZED`) |
| Счета (главный) | суммарный баланс, счёт с `availableMinor`, последние операции, быстрые действия |
| Перевод | выбор счёта списания, телефон получателя, сумма, комментарий; экран подтверждения с ключом идемпотентности; экран результата с номером платежа |
| История | список платежей с фильтром по статусу, детали с таймлайном переходов |
| Магазин | витрина с поиском и сортировкой, карточка товара: продавец, город, бренд, склад, резерв |
| Корзина | позиции, изменение количества, подытог |
| Оформление | адрес, контактный телефон, комментарий, счёт списания, экран «Заказ создан» |
| Заказы | список с фильтрами по статусу, детали заказа с платежами по мерчантам |

## 7. Тесты

```powershell
# JVM-тесты: деньги, телефоны, разбор problem-документов, ключ идемпотентности
.\gradlew.bat testDebugUnitTest

# те же тесты + 4 сценария против живого шлюза (нужен поднятый бэкенд на :8080)
.\gradlew.bat testDebugUnitTest "-Dtaxi.liveTest=true"
```

Живые тесты (`app/src/test/java/kz/taxi/mobile/live/LiveBackendTest.kt`) работают через
**тот же** `NetworkModule`, что и приложение: те же интерсепторы, DTO и сериализация,
только адрес — loopback хоста. Они сами себя пропускают, если флаг не передан, поэтому
обычный `gradlew test` не зависит от наличия бэкенда. Проверяется:

1. вход, `GET /auth/me`, список счетов, **реальный перевод** и повтор с тем же
   `Idempotency-Key` → тот же `paymentId` (и новый ключ → новый платёж);
2. отказ на неизвестного получателя: 404 `TARGET_ACCOUNT_NOT_FOUND` с `correlationId`,
   который подставлен в текст ошибки для поддержки;
3. неверный код → 401, «мёртвый» токен → 401 и сигнал слою сессии очистить её;
4. анонимная витрина → корзина (добавить/изменить/добавить) → checkout → заказ `PAID`
   с платежами по мерчантам, повтор checkout идемпотентен.

> Примечание по хрупкости: сценарий покупки берёт самый дешёвый товар, у которого хватает
> стока на весь сценарий (3 единицы). Без этого повторный прогон упирался в
> `PRODUCT_UNAVAILABLE`, потому что предыдущий прогон выкупал товар до нуля.

## 8. Идемпотентность в интерфейсе

Ключ идемпотентности — не деталь реализации, а часть интерфейса: он показан на экране
подтверждения и на экране результата, чтобы операция была воспроизводима при разборе
инцидента. Кнопка «Повторить операцию» намеренно **выпускает новый ключ** — это новый
перевод, а не повтор старого; повтор с прежним ключом делает клиент при сетевом сбое.

Проверено на живом стеке: перевод из приложения `P01M3W5ECJ2V9D6W04MR80JJJ5J` (250,00 ₸,
комиссия 0) прошёл и провёлся транзакцией в account-service; повтор того же ключа с **другим**
телом запроса шлюз отклонил как `409 IDEMPOTENCY_CONFLICT`, а в `payment.payment` по этому
ключу осталась ровно одна запись.

## 9. Безопасность

* Cleartext разрешён только для `10.0.2.2`, `localhost` и `127.0.0.1`
  (`network_security_config.xml`), `base-config` его запрещает — release-сборка не сможет
  незаметно уйти на HTTP в интернет.
* Токен и профиль лежат в DataStore private-хранилища приложения; ответ 401 приводит к
  очистке сессии и возврату на экран входа.
* Клиент не имеет внутренних привилегий: все вызовы идут через шлюз с обычным
  user-токеном, поэтому `403 FORBIDDEN_ACCOUNT_ACCESS` на чужой счёт он получает так же,
  как любой другой клиент.
