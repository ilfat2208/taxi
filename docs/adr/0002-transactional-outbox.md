# 0002. События через транзакционный outbox

**Статус:** принято

## Контекст

Сервис, изменивший состояние, должен сообщить об этом остальным. Наивный код
пишет в БД и в Kafka отдельно:

```java
paymentRepository.save(payment);   // ①
kafkaTemplate.send("payment.events", event);  // ②
```

Падение между ① и ② теряет событие (заказ никогда не узнает об оплате), падение
после ② с откатом ① создаёт «фантомное» событие (заказ сошлётся на платёж,
которого нет). Это классический dual write, и он не лечится порядком строк.

## Решение

Событие пишется в таблицу `outbox_message` в **той же транзакции**, что и
изменение агрегата. Отдельный relay (`OutboxRelay`) публикует строки в Kafka:

```java
@Transactional
public PaymentResponse complete(...) {
    payment.markCompleted();                     // домен
    paymentRepository.save(payment);
    outboxWriter.append(TOPIC, envelope);        // та же транзакция
    return mapper.toResponse(payment);
}
```

Relay забирает пачку через `SELECT ... FOR UPDATE SKIP LOCKED`, отправляет и
помечает `PUBLISHED` только после подтверждения брокера, затем сохраняет статус.
Доставка — at-least-once, дубли отсекаются на стороне консьюмера по `eventId`.

## Альтернативы

* **Kafka Transactions (EOS)** — не покрывает запись в БД; нужен всё равно outbox.
* **CDC (Debezium) по WAL** — рабочее решение, но требует инфраструктуры и
  отдельного маппинга «строка → событие»; outbox оставляет контракт в коде.
* **Прямая отправка + ретраи в памяти** — теряет событие при падении процесса.

## Последствия

* Задержка публикации — интервал опроса (по умолчанию 500 мс). Для денежных
  событий это приемлемо, для «живого» чата — нет.
* Таблица outbox требует уборки: опубликованные строки удаляются по ретеншну
  (`taxi.outbox.retention-days`).
* Строки с исчерпанными попытками (10 по умолчанию) остаются `FAILED` и ждут
  оператора — это осознанное решение вместо бесконечного ретрая, который
  останавливает партицию.
