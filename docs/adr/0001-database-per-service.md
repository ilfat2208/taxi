# 0001. Своя база данных у каждого сервиса

**Статус:** принято

## Контекст

Пять сервисов обмениваются данными: платёж меняет баланс, заказ резервирует сток
и запускает платёж, каталог публикует события об остатках. Соблазн — одна общая
база: тогда «всё в одной транзакции» и не нужны саги.

## Решение

У каждого сервиса своя база (`taxi_account`, `taxi_payment`, `taxi_catalog`,
`taxi_order`) и своя схема внутри неё. Никакой сервис не читает таблицы другого:
только HTTP API или события. Схема эволюционирует через Flyway, принадлежит
сервису и меняется вместе с ним.

## Почему не общая база

| Общая база | Своя база |
|---|---|
| «Бесплатная» ACID-транзакция между доменами | Транзакция только внутри домена, между — сага |
| Любая миграция ломает всех сразу | Миграция затрагивает один сервис |
| Нельзя выделить нагрузку и права по сервису | Свои пул, права, бэкап, ретеншн |
| Общая транзакция держит блокировки на чужом домене | Блокировки локальны |

Главный аргумент против общей базы — не производительность, а связность: общая
таблица превращает два независимых сервиса в один распределённый монолит, который
невозможно деплоить по частям.

## Последствия

* Между сервисами — согласованность в конечном счёте; в проекте это саги с
  компенсациями и идемпотентные операции.
* Нужны отчётные «сборки» данных: сейчас события Kafka, в реальной эксплуатации —
  отдельное read-хранилище/CDC.
* Локально всё поднимается одним `docker compose`, базы создаются init-скриптом
  `infra/postgres/init/01-databases.sql`.
