# 0005. Оркестрация checkout-саги в order-service

**Статус:** принято

## Контекст

Checkout затрагивает три сервиса: заказ (order), сток (catalog), деньги (payment).
Распределённой транзакции нет, значит нужна сага. У саги два стиля: оркестрация
(один сервис ведёт процесс) и хореография (сервисы реагируют на события друг друга).

## Решение

Оркестратор — `order-service`. Он выполняет шаги последовательно, хранит состояние
саги в самом заказе и в `order_status_history`, и компенсирует неудачи:

| Шаг | Действие | Компенсация при сбое следующего шага |
|---|---|---|
| 1 | создать заказ `PENDING_PAYMENT` | заказ → `FAILED` |
| 2 | зарезервировать сток | release резерва |
| 3 | платёж мерчанту | release резерва, заказ → `CANCELLED` |
| 4 | подтвердить заказ, commit стока | (после оплаты компенсация — возврат) |

Одновременно работает асинхронный контур: `order-service` слушает
`payment.completed` / `payment.failed` и доразбирает заказы, которые остались в
`PENDING_PAYMENT` (таймаут синхронного вызова, рестарт пода). Это не дублирование
шага 3, а страховка: единственным доказательством списания может оказаться именно
событие.

## Почему не хореография

При хореографии логика «что делать при отказе оплаты» размазывается по
обработчикам событий в разных сервисах. Понять, почему конкретный заказ завис,
можно только собрав цепочку. Оркестратор даёт:

* одно место, где видно весь процесс (класс + `order_status_history`);
* явные таймауты и детерминированное восстановление после падения;
* возможность менять порядок шагов, не трогая владельцев стока и денег.

Цена — `order-service` знает про API двух других сервисов. Для продукта, где
checkout и есть основная ценность, это приемлемо.

## Последствия

* Каждый шаг фиксируется в БД **до** следующего удалённого вызова: сага
  восстанавливается по состоянию БД, а не по состоянию в памяти.
* Резервы имеют TTL: даже если сага не смогла компенсировать, сток и деньги
  вернутся автоматически по истечении срока.
* Идемпотентность обязательна на обоих концах: `Idempotency-Key` для checkout и
  ключи, производные от `orderId`, для резерва и платежа.
