# 0003. Идемпотентность на двух уровнях

**Статус:** принято

## Контекст

Мобильный клиент ретраит запрос на плохой сети, пользователь дважды нажимает
«Перевести», брокер доставляет событие повторно, сага продолжает работу после
рестарта. Любой из этих случаев без защиты означает второе списание.

## Решение

Два независимых уровня, оба обязательны:

1. **`Idempotency-Key` (Redis, `SET NX`)** — протокол клиента с сервером.
   Первый запрос захватывает ключ, выполняет операцию и сохраняет ответ на 24 часа.
   * повтор с тем же телом → отдаётся сохранённый ответ (клиент не видит разницы);
   * повтор, пока первый ещё выполняется → `409 CONFLICT` («повторите через момент»);
   * тот же ключ с другим телом → `409 IDEMPOTENCY_CONFLICT` (это ошибка клиента,
     и её нельзя «тихо применить»);
   * операция упала → ключ освобождается, ретрай разрешён.
2. **Уникальные индексы в БД** — последняя линия обороны от гонки двух реплик:
   `payment.idempotency_key`, `account_hold.idempotency_key`,
   `stock_reservation(order_id, product_id)`.

Дополнительно внутренние операции идемпотентны по **бизнес-ссылке**: зачисление по
`(referenceType, referenceId)`, захват hold — по самому hold (повторный захват
возвращает исходную транзакцию из леджера), а не по клиентскому ключу, которого у
саги на этом шаге уже нет.

## Почему не один уровень

Только Redis: ошибка конфигурации/сброс кэша = двойные списания.
Только БД: пользователь получает `500 duplicate key` вместо своего результата,
а «в полёте» отличить от «уже выполнено» невозможно.

## Последствия

* Все деньги-двигающие эндпоинты требуют заголовок; без него — `400`.
* Реализация: `IdempotencyGuard.execute(key, requestBody, ResponseType.class, action)`
  и уникальные индексы в миграциях.
* Хранилище идемпотентности (Redis) становится критичным компонентом: недоступность
  Redis даёт `503`, а не «работаем без защиты».
