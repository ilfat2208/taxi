# 0004. Деньги — целые числа в минорных единицах

**Статус:** принято

## Контекст

Денежные суммы нужно складывать, делить (комиссия, проценты, доли), сравнивать и
хранить без потерь. Ошибка округления в платёжной системе — это расхождение
баланса, которое ищут неделями.

## Решение

Сумма — `long` в минорных единицах (тиын/центы) плюс явная валюта:

```java
Money fee = Money.ofMinor(total.minorUnits()).percentage(150); // 1.5%
long balanceMinor;                                             // в БД: BIGINT
currency VARCHAR(3);                                           // в БД: KZT/USD/EUR/RUB
```

* `double`/`float` запрещены полностью: 0.1 + 0.2 ≠ 0.3, а в деньгах это недопустимо.
* `BigDecimal` допустим только на границе (`Money.ofDecimal`) — при парсинге ввода,
  и сразу приводится к минорным единицам с округлением HALF_UP.
* Все операции с валютой проверяют её совпадение: `Money.plus` бросает
  `CurrencyMismatchException`, а не молча складывает тенге с долларами.
* Проценты считаются в базисных пунктах (1 bp = 0.01%) целочисленно, с явным
  округлением — «половина вверх», как принято в розничных расчётах.

## Почему не `NUMERIC(19,4)` в БД

Десятичный тип тоже корректен, но требует дисциплины на каждом шаге (масштаб,
округление при сравнении, поведение разных драйверов) и не мешает случайно
сложить `BigDecimal` c разным scale. Целые единицы делают ошибку невозможной:
складывать можно только целые одного масштаба, а масштаб задаёт валюта.

## Последствия

* Колонки `*_minor BIGINT`, в JSON — `amountMinor`, `balanceMinor`, `totalMinor`.
* Клиент обязан делить на 100 только для отображения (в web это `Intl.NumberFormat`).
* В интерфейсах сервисов сумма — `Money`, в сущностях — `long`: конвертация ровно
  в одном месте.
* KZT формально имеет 2 знака; если появится валюта с другим масштабом (JPY, KWD),
  `Currency.scale()` уже это учитывает.
